# ADR-009 — PostgreSQL migration without a production cutover

> Status update — 2026-08-20: Railway now runs on PostgreSQL and the owned
> event, finance, access and Patch product tables are durable there. The
> historical Airtable operational tables have been copied and reconciled into
> `ops_*`. The legacy order/driver/dispatch repository still reads and writes
> Airtable while the final repository switch is built. Therefore this ADR is
> **implemented for infrastructure and owned domains, but not yet complete for
> legacy order truth**. Airtable must not be removed or described as a mere
> mirror until those call sites have moved and the failure drills pass.

**Status:** ACCEPTED, CUTOVER NOT COMPLETE · updated 2026-08-20

## Decision

GateWay/Patch will move operational ownership to PostgreSQL in reversible stages. Airtable and the production SQLite database remain unchanged until their records have been copied, reconciled, backed up, and exercised in a staging deployment.

The first deployment adds migration tooling and PostgreSQL support only. It does not change the production read or write path.

## Current production reality

- Airtable is the operational source for customers, orders, drivers, deliveries, and dispatch events.
- The Railway application service still has no `DATABASE_URL`, so the application's
  owned tables use `/app/nucleus_events.db`. A separate `Postgres-RITE` service is
  online but had no tables when inspected on 2026-08-20. Application `/healthz`
  previously described any successful SQL connection as `db: up`; v1.9.39 adds the
  non-secret `db_backend` and `db_durable` facts so SQLite cannot be mistaken for
  PostgreSQL again.
- The live SQLite database contains partner, menu, option, driver-profile, promo-code, event, and other application-owned records. These must be migrated before `DATABASE_URL` is attached.
- Airtable contains duplicate human-readable order IDs. Airtable record IDs are therefore preserved as the durable migration key.

## Migration gates

1. Create a point-in-time backup and inventory of the live SQLite database.
2. Provision an isolated PostgreSQL service and connect it to a staging deployment.
3. Run the Airtable migrator in `--dry-run` mode.
4. Copy SQLite-owned tables to PostgreSQL and compare table-by-table counts and primary keys.
5. Run the Airtable migrator with `--apply`; verify source counts, target counts, links, and duplicate order IDs.
6. Exercise staging order intake, dispatch, menus, partner pages, driver flows, notifications, and restart persistence.
7. Add dual-write with an outbox/retry mechanism and observe it before changing reads.
8. Switch reads behind a feature flag, retain rollback access to the prior stores, and reconcile after cutover.
9. Retire Airtable from the transactional path only after an agreed observation period. It may remain a reporting or operator view.

## Safety rules

- Migration commands never delete or edit Airtable records.
- No target row is keyed solely by the human order number.
- Every import is repeatable and produces a recorded reconciliation result.
- Production code and schema changes are deployed through a branch, staging environment, and feature flags.
- Git rollback is not treated as a database rollback. Database backups and backward-compatible migrations are required separately.

- Driver profiles: 3

The v1.9.38 and v1.9.40 snapshots have disjoint generated IDs for all menu,
option, and event rows. Importing both complete files would therefore duplicate
400 menu items, 153 option groups, and 765 option choices. The rehearsed recovery
sequence is instead:

1. Import the complete v1.9.40 snapshot as the current catalog.
2. Merge only the append-only `events` table from v1.9.38.
3. Reconcile the result at 10 partners, 400 menu items, 153 option groups,
   765 option choices, 3 driver profiles, 2 promo codes, and 5 owned events.

The migration CLI's `--merge-events` mode implements this narrow recovery path,
never updates an existing event, and permits newer event rows already in the
target. The exact two-snapshot sequence was rehearsed successfully against a
disposable target database before any production transfer.
